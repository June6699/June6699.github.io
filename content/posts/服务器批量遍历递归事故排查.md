## 0. 事故现场

9 月 30 日凌晨，我有个服务器突然挂了。

这里把排查记录、原因、修复方式以及一些教训写下来，也方便后面复习一些命令的使用。

- ping IP是通的
- TCP 22 能建立
- SSH 客户端显示 `Connection established`
- 然后卡在 banner exchange，永远等不到登录提示

这种情况通常只有一个原因：系统资源耗尽了，服务器卡的受不了，腾不出手接收 ssh 请求。

## 1. 最开始的线索：pigz

重启前系统日志里有大量这样的警告：

```bash
$ journalctl --boot=-1 --since "2026-09-30 00:10" | grep "shell level"
Sep 30 00:17:23 bash: warning: shell level (1000) too high, resetting to 1
Sep 30 00:17:24 bash: warning: shell level (1000) too high, resetting to 1
Sep 30 00:17:25 bash: warning: shell level (1000) too high, resetting to 1
...（数千条）
```

SHLVL 是 shell 的嵌套层级，这里的`shell level`对应环境变量 `SHLVL`，正常情况下不会超过 10。到 1000 说明 bash 在疯狂递归调用自己。

- 这里的日志一直`warning 1000` 是因为`Bash`内置了安全阈值，当嵌套层级达到1000时，会被判定出现了无限递归，会把层级重置为1，避免栈溢出导致进程崩溃。
- 这里几千条重复`warning`说明系统中存在持续的、快速的、无限的、递归的`Shell`调用。由此我们可以知道，之前的内存爆了就是由于这种`shell`一直无限的生成导致的，那么我们考虑以下几种可能。
  - **脚本自调用**：某个脚本里面，没有终止条件地调用了自己，然后又调用自己，一直不干正事，就在那一直调用。比如有一个脚本`run.sh`，里面内容里面又写着`/path/to/run.sh`，也有可能就是`./run.sh`，执行后就会无限递归生成子进程调用自己。
  - **配置文件循环加载**：用户环境配置文件（`~/.bashrc`、`~/.bash_profile`）或系统配置（`/etc/profile`）中，错误地循环 `source` 了自身，或者两个配置文件互相 source，每次启动 bash 都会触发嵌套。
  - **`bash`被污染/替换**：给 `bash` 命令设置了别名，或者定义了名为 `bash` 的函数，内部又调用了 `bash` 命令，导致每次执行 bash 都会无限嵌套。
  - **定时任务/自启动脚本有bug**：crontab 或开机自启服务中，存在有递归 bug 的脚本，到点触发后就持续在后台疯跑。

          └─ bash -c pigz -
              └─ bash -c pigz -
                  └─ bash -c pigz -

## 2. 递归的机制

当一个程序不是 ELF 可执行文件，也不是 `#!` 开头的脚本时，kernel 会把它当作 shell 脚本交给 `/bin/sh` 执行。

所以当你执行 `pigz file.txt` 时：

```
1. kernel 读取 /usr/bin/pigz
2. 发现内容是 "pigz -"
3. 启动 /bin/sh 执行这行文本
4. sh 执行：pigz -
5. 通过 PATH 再次找到 /usr/bin/pigz
6. 回到步骤 1
7. 无限的pigz在调用shell去找pigz并执行这个错误的pigz，OOM出现
```

每次递归都会：
- 创建新的 bash 进程
- 分配内存
- SHLVL + 1

最终结果就是进程数暴增、内存耗尽。

用 `file` 命令批量检查：

## 5. 根本原因推测

回想 9 月 18 日那天，我在让 AI 帮忙安装生信工具包。

AI 很可能通过 SSH 管道执行了类似这样的命令：

```bash
echo "
for tool in gcc git samtools tabix pigz unpigz R Rscript python3 make; do
    echo \"\$tool -\" > /usr/local/bin/\$tool
    chmod +x /usr/local/bin/\$tool
    cat >> /usr/local/bin/\$tool << 'EOF'
#!/bin/bash
exec /conda/bin/\$tool \"\$@\"
EOF
done
" | ssh root@server bash
```

AI 的本意可能是创建 wrapper 脚本，让系统级命令指向 Conda 环境中的工具。

- 这里`echo`这么多`\`是为了防止把`”`当做第一个`echo "`后面的那个`”`当做一对，实际上这整个是为了ssh后再执行的。

脚本逻辑是：
1. 先写入 `tool -` 作为占位符
2. 再追加完整的 wrapper 内容

但我在执行到一半时按了 Ctrl+C。

结果：
- `echo "$tool -" >` 已执行（覆盖了原文件）
- 后面的 `cat >>` 未执行（完整内容没写入）
- 留下一堆只有一行 `xxx -` 的文件

### 为什么是管道命令特别危险？

SSH 管道的数据传输是流式的：

```
本地脚本 → 本地 SSH 缓冲 → 网络 → 远程 SSH 缓冲 → 远程 bash stdin
```

中断时：
- 本地停止发送
- 但远程会继续执行已接收的部分
- 后面的内容永远不会到达

如果脚本是个 `for` 循环，中断可能发生在循环的第 7 次迭代，结果就是前 7 个工具被改坏，后面的保持原样。

这也解释了为什么只有部分文件被改写。

## 6. 9 月 30 日为什么又出问题

9 月 18 日事故后，我发现了这个问题，并修复了部分文件，并反复检查还有没有：

- `perm /111`：找权限，`user   group   other`里面权限只要有一个是1（执行权限）就算，`/`就是这个功能

  r = read     读	4
  w = write    写	2
  x = execute  执行	1

- `size -1k`：文件必须小于1kb

- `read -r`：不要把`\`当做转义符处理，即原样读取内容，然后读取变量放到`f`

- `basename`：把`f=/usr/local/bin/x86_64-pc-linux-gnu-gcc`变成`name=x86_64-pc-linux-gnu-gcc`，因为我们文件里面是`pigz -`，而不是`usr/local/bin/pigz -`

- 最后判断文件内容是不是`/xxx/bin/{tool}`里面的内容是`{tool} -`的格式，如果是，就输出`{tool}: /xxx/bin/{tool} -`的格式

- `2>/dev/null`是为了丢掉error，不想看报错

  0 = 标准输入 stdin
  1 = 标准输出 stdout
  2 = 标准错误 stderr

```shell
for d in /usr/bin /usr/local/bin; do
    find "$d" -maxdepth 1 -type f -perm /111 -size -1k |
    while read -r f; do
        name=$(basename "$f")
        if [ "$(cat "$f" 2>/dev/null)" = "$name -" ]; then
            echo "$f: $name -"
        fi
    done
done
```

发现

- gcc ✓
- samtools ✓
- tabix ✓

但**漏掉了 git、unpigz**。

可能是因为：
- 我不常用 unpigz（通常只用 pigz 压缩）
- 检查时主要看了 `/usr/local/bin`，漏掉了 `/usr/bin`
- 文件太多，没有全部检查

9 月 30 日凌晨，某个下载任务脚本调用了 `unpigz` 或 `pigz`，触发了递归，系统再次崩溃。

## 9. 教训

### 9.1 管道命令要小心

不要通过 SSH 管道执行复杂的批量操作，尤其是会覆盖系统文件的操作。

更安全的做法：
```bash
# 先写到临时文件
cat > /tmp/wrapper_$tool << 'EOF'
#!/bin/bash
exec /conda/bin/$tool "$@"
EOF

# 验证文件完整
if [ -s /tmp/wrapper_$tool ]; then
    # 原子性地移动
    mv /tmp/wrapper_$tool /usr/local/bin/$tool
    chmod +x /usr/local/bin/$tool
fi
```

但其实最关键做法就是不要动`/usr/bin`和`/usr/local/bin`的东西

### 9.2 中断后要全面检查

如果中断了一个批量操作，不要只检查"看起来有问题"的文件。

应该：
```bash
# 检查最近修改的小文件
find /usr/bin /usr/local/bin -type f -mmin -10 -size -1k

# 检查是否有异常的文本文件
find /usr/bin /usr/local/bin -type f -exec file {} \; | grep -v ELF
```

### 9.3 关键文件要保护

可以考虑对关键系统命令加 immutable 属性：

```bash
chattr +i /usr/bin/git
chattr +i /usr/bin/pigz
```

但要注意：
- 正常的系统更新也会失败
- 升级前需要先 `chattr -i`

### 9.4 备份很重要

在执行可能影响系统的操作前，先备份关键文件：

```bash
cp -p /usr/bin/{git,pigz,gcc} /root/backup/
```

## 10. 技术细节补充

### 10.1 为什么是 "xxx -" 而不是其他内容

这可能是 AI 生成的脚本中的占位符写法。

`-` 在很多命令中表示"从 stdin 读取"，所以 `pigz -` 的意思本来应该是"从标准输入读取数据并压缩"。

但当这行文本被 shell 解释执行时，它会通过 PATH 再次查找 `pigz` 命令，如果找到的还是同一个损坏的文件，就形成了递归。

我们可以手动验证这个机制：

```bash
# 创建一个测试目录
$ mkdir /tmp/test_recursion
$ cd /tmp/test_recursion

# 创建一个"损坏"的命令
$ echo "testcmd -" > testcmd
$ chmod +x testcmd

# 把当前目录加到 PATH 最前面
$ export PATH="/tmp/test_recursion:$PATH"

# 执行这个命令（注意：这会快速消耗资源，立即 Ctrl+C）
$ timeout 2 ./testcmd 2>&1 | head -20
bash: warning: shell level (1000) too high, resetting to 1
bash: warning: shell level (1000) too high, resetting to 1
...
```

可以看到和我们服务器上一样的递归警告。

清理测试：

```bash
$ cd ~
$ rm -rf /tmp/test_recursion
$ export PATH=$(echo $PATH | sed 's|/tmp/test_recursion:||')
```

### 10.2 SHLVL 的含义

`SHLVL` 是 shell 的嵌套层级。可以这样观察：

```bash
$ echo $SHLVL
1

$ bash -c 'echo $SHLVL'
2

$ bash -c 'bash -c "echo $SHLVL"'
3

$ bash -c 'bash -c "bash -c \"echo \$SHLVL\""'
4
```

正常情况下：
- 登录 shell：SHLVL=1
- 在 shell 中启动子 shell：SHLVL=2

递归调用会导致 SHLVL 不断增加：

```bash
# 模拟递归（小心！会快速增长）
$ (bash -c 'for i in {1..10}; do bash -c "echo SHLVL=\$SHLVL"; done')
SHLVL=2
SHLVL=2
SHLVL=2
...
```

bash 在达到 1000 时会重置并输出警告：

```
bash: warning: shell level (1000) too high, resetting to 1
```

这是 bash 的自我保护机制，但重置后递归还会继续。

### 10.3 为什么 SSH 登录不了

用 `ss` 命令看 TCP 连接状态：

```bash
$ ss -tn | grep :22
ESTAB  0  0  server_ip:22  client_ip:54321
```

连接是 `ESTAB`（已建立）状态，但卡在那里了。

当系统内存和进程数耗尽时：

```bash
# 当时的资源状态（从 sar 重建）
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           754G        752G        788M         12G        1.2G         200M
Swap:          4.0G        4.0G          0B
```

此时：
- kernel 仍能处理网络包（所以 ping 通，TCP 能建立）
- 但 sshd 无法 fork 出新进程处理登录

```bash
# sshd 的日志（事故时）
$ journalctl -u sshd --boot=-1 --since "00:15" --until "00:20"
Sep 30 00:17:23 sshd[12345]: Accepted connection from client_ip port 54321
Sep 30 00:17:23 sshd[12345]: error: fork: Cannot allocate memory
Sep 30 00:17:45 sshd[12346]: Accepted connection from client_ip port 54322
Sep 30 00:17:45 sshd[12346]: error: fork: Cannot allocate memory
```

即使 fork 成功，也可能因为内存不足无法分配 PTY：

```bash
Sep 30 00:18:12 sshd[12389]: error: pty_allocate: Cannot allocate memory
```

最终表现就是：
- 客户端：`Connection established` 后卡住
- 服务端：sshd 无法创建会话
- 结果：永远等不到登录提示

验证当前系统可用资源（恢复后）：

```bash
$ cat /proc/sys/kernel/pid_max
4194304

$ ps -e --no-headers | wc -l
1145

$ echo "当前进程数占 PID 空间的比例: $(echo "scale=2; 1145/4194304*100" | bc)%"
当前进程数占 PID 空间的比例: 0.02%
```

正常情况下进程数占用不到 0.1%，事故时达到了 0.6%（25,462 / 4,194,304）。

### 10.4 内存是怎么被吃光的

每个 bash 进程大约占用：

```bash
$ ps aux | grep bash | head -1 | awk '{print $6}'
3456

# 单位是 KB，转换成 MB
$ echo "scale=2; 3456/1024" | bc
3.38
```

单个 bash 进程约 3.38 MB。

如果有 25,462 个 bash 进程：

```bash
$ echo "scale=2; 25462 * 3.38 / 1024" | bc
84.03
```

bash 本身占用约 84 GB。

但还有进程栈、文件描述符、内核数据结构等开销：

```bash
# 查看进程限制
$ ulimit -a | grep -E "open files|max user processes|stack size"
open files                      (-n) 1048576
max user processes              (-u) 772700
stack size              (kbytes, -s) 8192
```

每个进程：
- 栈：8 MB
- 文件描述符表：若干 KB
- task_struct 等内核结构：~1-2 KB

粗略计算（25,462 个进程）：

```bash
$ echo "scale=2; 25462 * (3.38 + 8 + 0.1) / 1024" | bc
285.73
```

约 285 GB，这还没算上其他正常进程和系统开销。

加上正常的生信任务（一些任务本身就占几十 GB 内存），754 GB 被吃光就不奇怪了。

## 11. 总结

这次事故的完整链条：

```
9月18日 AI 帮忙安装工具
    ↓
通过 SSH 管道执行批量脚本
    ↓
脚本先写 "xxx -" 占位符，再写完整内容
    ↓
执行到一半被 Ctrl+C 中断
    ↓
多个系统命令只剩下 "xxx -"
    ↓
修复了部分文件，但漏掉了 pigz/unpigz
    ↓
9月30日 某任务调用 unpigz
    ↓
触发 pigz 无限递归
    ↓
bash 进程暴增，内存耗尽
    ↓
SSH 无法登录，只能重启
```

核心问题不是某个程序的 bug，而是：
1. 脚本设计不当（先覆盖文件，再写内容）
2. 操作被中断（没有原子性保证）
3. 检查不彻底（漏掉了部分损坏文件）

最终的解决办法也很直接：
- 恢复所有损坏的文件
- 全面检查确保没有遗漏
- 以后避免用管道执行危险操作

754 GiB 内存能被吃光，不是因为某个程序占用太多，而是因为几万个 bash 进程同时存在。

这次事故提醒我：系统维护不能只看"当前有问题的地方"，而要全面检查"可能被影响的所有地方"。
