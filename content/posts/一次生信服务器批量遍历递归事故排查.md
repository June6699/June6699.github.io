## 0. 事故现场

9 月 30 日凌晨，生信服务器突然挂了。

症状很经典：
- ping 通
- TCP 22 能建立
- SSH 客户端显示 `Connection established`
- 然后卡在 banner exchange，永远等不到登录提示

这种情况通常只有一个原因：系统资源耗尽了。

重启后登上去一看，sar 历史记录显示凌晨 00:17 时：
- 进程数：25,462 个
- 内存占用：99.87%（754 GiB 几乎全满）
- Swap：100%（4 GiB 也满了）

服务器配置是 96 核心、754 GiB 内存，正常情况下进程数在 1100 左右。

这不是第一次了。9 月 18 日也发生过类似的事故。

## 1. 最开始的线索：pigz

登录后检查日志，发现有大量这样的进程残留：

```bash
bash -c cd /data/xxx/inputs/PR/raw && pigz -f PR_1000g_GWAS_EUR.txt ...
```

而且都是 bash 调用 pigz，SHLVL 层级非常深，有的甚至达到 1000。

bash 会在 shell 层级过高时输出警告：

```
bash: warning: shell level (1000) too high, resetting to 1
```

这说明 bash 在疯狂递归调用自己。

检查 `/usr/bin/pigz`：

```bash
$ file /usr/bin/pigz
/usr/bin/pigz: ASCII text

$ cat /usr/bin/pigz
pigz -
```

只有 7 字节。

## 2. 递归的机制

当一个程序不是 ELF 可执行文件，也不是 `#!` 开头的脚本时，kernel 会把它当作 shell 脚本交给 `/bin/sh` 执行。

所以当你执行 `pigz file.txt` 时：

```
1. kernel 读取 /usr/bin/pigz
2. 发现内容是 "pigz -"
3. 启动 /bin/sh 执行这行文本
4. sh 执行：pigz -
5. 通过 PATH 再次找到 /usr/bin/pigz
6. 回到步骤 1
```

无限递归。

每次递归都会：
- 创建新的 bash 进程
- 分配内存
- SHLVL + 1

最终结果就是进程数暴增、内存耗尽。

## 3. 不止 pigz

检查其他常用命令，发现问题更严重：

```bash
$ ls -lh /usr/bin/git /usr/bin/unpigz
-rwxr-xr-x 1 root root 7 Sep 18 17:47 /usr/bin/git
-rwxr-xr-x 1 root root 7 Sep 18 17:47 /usr/bin/unpigz
```

都是 7 字节，内容都是：

```
git -
unpigz -
```

再看 `/usr/local/bin`：

```bash
$ find /usr/local/bin -type f -size -100c -exec file {} \;
/usr/local/bin/gcc: ASCII text, 6 bytes
/usr/local/bin/x86_64-pc-linux-gnu-gcc: ASCII text, 6 bytes
/usr/local/bin/samtools: ASCII text, 11 bytes
```

内容分别是：

```
gcc -
gcc -
samtools -
```

甚至之前删除的某个 Conda 环境（IReNA）里，R、Rscript、python3、make 也都变成了这种格式。

所有这些文件的修改时间都集中在：**2026-09-18 17:47**

## 4. 9 月 18 日发生了什么

那是第一次事故。

当时除了文件被改写，还有两个脚本在疯狂运行：
- `/tmp/check2.sh`：数千实例
- `process_ready_bams.sh`：数千实例

`check2.sh` 最开始的内容是统计进程数量的监控脚本，但它自己形成了递归。后来把它改成了：

```bash
#!/bin/bash
exit 0
```

并加了 immutable 属性防止被修改。

`process_ready_bams.sh` 是一个正常的后台任务脚本，本身没问题，但它会调用 samtools，而 samtools 已经被改坏了，所以也成了递归链的一部分。

## 5. 根本原因推测

回想 9 月 18 日那天，我在让 AI 帮忙安装生信工具包。

AI 很可能通过 SSH 管道执行了类似这样的命令：

```bash
echo "
for tool in gcc git samtools tabix pigz unpigz R Rscript python3 make; do
    echo \"\$tool -\" > /usr/local/bin/\$tool
    chmod +x /usr/local/bin/\$tool
    cat >> /usr/local/bin/\$tool << 'EOF'
#!/bin/bash
exec /conda/bin/\$tool \"\$@\"
EOF
done
" | ssh root@server bash
```

AI 的本意可能是创建 wrapper 脚本，让系统级命令指向 Conda 环境中的工具。

脚本逻辑是：
1. 先写入 `tool -` 作为占位符
2. 再追加完整的 wrapper 内容

但我在执行到一半时按了 Ctrl+C。

结果：
- `echo "$tool -" >` 已执行（覆盖了原文件）
- 后面的 `cat >>` 未执行（完整内容没写入）
- 留下一堆只有一行 `xxx -` 的文件

### 为什么是管道命令特别危险？

SSH 管道的数据传输是流式的：

```
本地脚本 → 本地 SSH 缓冲 → 网络 → 远程 SSH 缓冲 → 远程 bash stdin
```

中断时：
- 本地停止发送
- 但远程会继续执行已接收的部分
- 后面的内容永远不会到达

如果脚本是个 `for` 循环，中断可能发生在循环的第 7 次迭代，结果就是前 7 个工具被改坏，后面的保持原样。

这也解释了为什么只有部分文件被改写。

## 6. 9 月 30 日为什么又出问题

9 月 18 日事故后，我修复了部分文件：
- gcc ✓
- samtools ✓
- tabix ✓

但**漏掉了 git、pigz、unpigz**。

可能是因为：
- 我不常用 unpigz（通常只用 pigz 压缩）
- 检查时主要看了 `/usr/local/bin`，漏掉了 `/usr/bin`
- 文件太多，没有全部检查

9 月 30 日凌晨，某个下载任务脚本调用了 `unpigz` 或 `pigz`，触发了递归，系统再次崩溃。

## 7. 修复过程

### 7.1 恢复损坏的文件

**git:**
```bash
dnf reinstall -y git
```

**pigz 和 unpigz:**

本来想用 `dnf reinstall pigz`，但 CentOS 8 Stream 的 vault 仓库返回 403，安装失败。

最后从 Conda 环境复制了一份：

```bash
cp /data/xujun/miniconda/envs/xj_gwas/bin/pigz /usr/bin/pigz
chmod 755 /usr/bin/pigz
ln -sf pigz /usr/bin/unpigz
```

**验证:**
```bash
file /usr/bin/pigz
# /usr/bin/pigz: ELF 64-bit LSB executable

pigz --version
# pigz 2.8
```

### 7.2 清理残留证据文件

把 `/usr/local/bin` 中异常的 gcc 相关文件移到证据目录：

```bash
mkdir -p /root/incident_evidence_20260918
mv /usr/local/bin/gcc.recursive.* /root/incident_evidence_20260918/
mv /usr/local/bin/x86_64-pc-linux-gnu-gcc* /root/incident_evidence_20260918/
```

这些文件的 mtime 都是 2026-09-18 17:47，是关键证据。

### 7.3 全面检查

检查所有小于 100 字节的可执行文件：

```bash
find /usr/bin /usr/local/bin -type f -size -100c -exec file {} \;
```

确认没有遗漏。

## 8. 为什么没有设置监控

最开始我加了完整性检查和进程监控，但后来觉得：
- 资源占用虽然很小，但不想要任何后台任务
- 这次事故应该是偶然的
- 已经修复了所有损坏文件，不太可能再发生

所以最后把监控都删除了。

如果以后再出现类似问题，可以考虑：
- 用 `auditd` 监控关键文件的写入操作
- 定期检查关键命令是否是正常 ELF 文件
- 进程数量超过阈值时触发告警

## 9. 教训

### 9.1 管道命令要小心

不要通过 SSH 管道执行复杂的批量操作，尤其是会覆盖系统文件的操作。

更安全的做法：
```bash
# 先写到临时文件
cat > /tmp/wrapper_$tool << 'EOF'
#!/bin/bash
exec /conda/bin/$tool "$@"
EOF

# 验证文件完整
if [ -s /tmp/wrapper_$tool ]; then
    # 原子性地移动
    mv /tmp/wrapper_$tool /usr/local/bin/$tool
    chmod +x /usr/local/bin/$tool
fi
```

### 9.2 中断后要全面检查

如果中断了一个批量操作，不要只检查"看起来有问题"的文件。

应该：
```bash
# 检查最近修改的小文件
find /usr/bin /usr/local/bin -type f -mmin -10 -size -1k

# 检查是否有异常的文本文件
find /usr/bin /usr/local/bin -type f -exec file {} \; | grep -v ELF
```

### 9.3 关键文件要保护

可以考虑对关键系统命令加 immutable 属性：

```bash
chattr +i /usr/bin/git
chattr +i /usr/bin/pigz
```

但要注意：
- 正常的系统更新也会失败
- 升级前需要先 `chattr -i`

### 9.4 备份很重要

在执行可能影响系统的操作前，先备份关键文件：

```bash
cp -p /usr/bin/{git,pigz,gcc} /root/backup/
```

## 10. 技术细节补充

### 10.1 为什么是 "xxx -" 而不是其他内容

这可能是 AI 生成的脚本中的占位符写法。

`-` 在很多命令中表示"从 stdin 读取"，所以 `pigz -` 的意思本来应该是"从标准输入读取数据并压缩"。

但当这行文本被 shell 解释执行时，它会通过 PATH 再次查找 `pigz` 命令，如果找到的还是同一个损坏的文件，就形成了递归。

### 10.2 SHLVL 的含义

`SHLVL` 是 shell 的嵌套层级。

正常情况下：
- 登录 shell：SHLVL=1
- 在 shell 中启动子 shell：SHLVL=2

递归调用会导致 SHLVL 不断增加，bash 在达到 1000 时会重置并输出警告。

### 10.3 为什么 SSH 登录不了

当系统内存和进程数耗尽时：
- kernel 仍能处理网络包（所以 ping 通，TCP 能建立）
- 但 sshd 无法 fork 出新进程处理登录
- 即使 fork 成功，也可能因为内存不足无法分配 PTY
- 最终表现就是连接建立，但卡在 banner 阶段

## 11. 总结

这次事故的完整链条：

```
9月18日 AI 帮忙安装工具
    ↓
通过 SSH 管道执行批量脚本
    ↓
脚本先写 "xxx -" 占位符，再写完整内容
    ↓
执行到一半被 Ctrl+C 中断
    ↓
多个系统命令只剩下 "xxx -"
    ↓
修复了部分文件，但漏掉了 pigz/unpigz
    ↓
9月30日 某任务调用 unpigz
    ↓
触发 pigz 无限递归
    ↓
bash 进程暴增，内存耗尽
    ↓
SSH 无法登录，只能重启
```

核心问题不是某个程序的 bug，而是：
1. 脚本设计不当（先覆盖文件，再写内容）
2. 操作被中断（没有原子性保证）
3. 检查不彻底（漏掉了部分损坏文件）

最终的解决办法也很直接：
- 恢复所有损坏的文件
- 全面检查确保没有遗漏
- 以后避免用管道执行危险操作

754 GiB 内存能被吃光，不是因为某个程序占用太多，而是因为几万个 bash 进程同时存在。

这次事故提醒我：系统维护不能只看"当前有问题的地方"，而要全面检查"可能被影响的所有地方"。
