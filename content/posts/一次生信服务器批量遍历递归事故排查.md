## 0. 事故现场

9 月 30 日凌晨，生信服务器突然挂了。

症状很经典：
- ping 通
- TCP 22 能建立
- SSH 客户端显示 `Connection established`
- 然后卡在 banner exchange，永远等不到登录提示

这种情况通常只有一个原因：系统资源耗尽了。

重启后登上去，先看看系统基本状态：

```bash

$ ps -e --no-headers | wc -l
1145

$ uptime
23:10:15 up 4 min,  1 user,  load average: 0.35, 0.89, 0.42
```

正常了。但事故发生时是什么样？用 sar 看历史数据：


## 1. 最开始的线索：pigz

重启前系统日志里有大量这样的警告：

```bash
$ journalctl --boot=-1 --since "2026-09-30 00:10" | grep "shell level"
Sep 30 00:17:23 bash: warning: shell level (1000) too high, resetting to 1
Sep 30 00:17:24 bash: warning: shell level (1000) too high, resetting to 1
Sep 30 00:17:25 bash: warning: shell level (1000) too high, resetting to 1
...（数千条）
```

SHLVL 是 shell 的嵌套层级，正常情况下不会超过 10。到 1000 说明 bash 在疯狂递归调用自己。

看看当时的进程树（从日志重建）：

```
systemd
  └─ bash /data/scripts/download.sh
      └─ bash -c pigz file.txt
          └─ bash -c pigz -
              └─ bash -c pigz -
                  └─ bash -c pigz -
                      └─ ... (无限递归)
```

问题出在 pigz 上。检查这个文件：

```bash
$ ls -lh /usr/bin/pigz
-rwxr-xr-x 1 root root 7 Sep 18 17:47 /usr/bin/pigz
```

只有 7 字节？正常的 pigz 应该是几十 KB 的 ELF 可执行文件。

```bash
$ file /usr/bin/pigz
/usr/bin/pigz: ASCII text

$ cat /usr/bin/pigz
pigz -

$ wc -c /usr/bin/pigz
7 /usr/bin/pigz
```

文件内容只有一行：`pigz -`

这就是递归的根源。

## 2. 递归的机制

当一个程序不是 ELF 可执行文件，也不是 `#!` 开头的脚本时，kernel 会把它当作 shell 脚本交给 `/bin/sh` 执行。

所以当你执行 `pigz file.txt` 时：

```
1. kernel 读取 /usr/bin/pigz
2. 发现内容是 "pigz -"
3. 启动 /bin/sh 执行这行文本
4. sh 执行：pigz -
5. 通过 PATH 再次找到 /usr/bin/pigz
6. 回到步骤 1
```

无限递归。

每次递归都会：
- 创建新的 bash 进程
- 分配内存
- SHLVL + 1

最终结果就是进程数暴增、内存耗尽。

## 5. 根本原因推测

回想 9 月 18 日那天，我在让 AI 帮忙安装生信工具包。

AI 很可能通过 SSH 管道执行了类似这样的命令：

```bash
echo "
for tool in gcc git samtools tabix pigz unpigz R Rscript python3 make; do
    echo \"\$tool -\" > /usr/local/bin/\$tool
    chmod +x /usr/local/bin/\$tool
    cat >> /usr/local/bin/\$tool << 'EOF'
#!/bin/bash
exec /conda/bin/\$tool \"\$@\"
EOF
done
" | ssh root@server bash
```

AI 的本意可能是创建 wrapper 脚本，让系统级命令指向 Conda 环境中的工具。

脚本逻辑是：
1. 先写入 `tool -` 作为占位符
2. 再追加完整的 wrapper 内容

但我在执行到一半时按了 Ctrl+C。

结果：
- `echo "$tool -" >` 已执行（覆盖了原文件）
- 后面的 `cat >>` 未执行（完整内容没写入）
- 留下一堆只有一行 `xxx -` 的文件

### 为什么是管道命令特别危险？

SSH 管道的数据传输是流式的：

```
本地脚本 → 本地 SSH 缓冲 → 网络 → 远程 SSH 缓冲 → 远程 bash stdin
```

中断时：
- 本地停止发送
- 但远程会继续执行已接收的部分
- 后面的内容永远不会到达

如果脚本是个 `for` 循环，中断可能发生在循环的第 7 次迭代，结果就是前 7 个工具被改坏，后面的保持原样。

这也解释了为什么只有部分文件被改写。

## 8. 为什么没有设置监控

最开始我加了完整性检查和进程监控，但后来觉得：
- 资源占用虽然很小，但不想要任何后台任务
- 这次事故应该是偶然的

所以最后把监控都删除了。

如果以后再出现类似问题，可以考虑：
- 用 `auditd` 监控关键文件的写入操作
- 定期检查关键命令是否是正常 ELF 文件
- 进程数量超过阈值时触发告警

## 9. 教训

### 9.1 管道命令要小心

不要通过 SSH 管道执行复杂的批量操作，尤其是会覆盖系统文件的操作。

更安全的做法：
```bash
# 先写到临时文件
cat > /tmp/wrapper_$tool << 'EOF'
#!/bin/bash
exec /conda/bin/$tool "$@"
EOF

# 验证文件完整
if [ -s /tmp/wrapper_$tool ]; then
    # 原子性地移动
    mv /tmp/wrapper_$tool /usr/local/bin/$tool
    chmod +x /usr/local/bin/$tool
fi
```

### 9.2 中断后要全面检查

如果中断了一个批量操作，不要只检查"看起来有问题"的文件。

应该：
```bash
# 检查最近修改的小文件
find /usr/bin /usr/local/bin -type f -mmin -10 -size -1k

# 检查是否有异常的文本文件
find /usr/bin /usr/local/bin -type f -exec file {} \; | grep -v ELF
```

### 9.3 关键文件要保护

可以考虑对关键系统命令加 immutable 属性：

```bash
chattr +i /usr/bin/git
chattr +i /usr/bin/pigz
```

但要注意：
- 正常的系统更新也会失败
- 升级前需要先 `chattr -i`

### 9.4 备份很重要

在执行可能影响系统的操作前，先备份关键文件：

```bash
cp -p /usr/bin/{git,pigz,gcc} /root/backup/
```

## 10. 技术细节补充

### 10.1 为什么是 "xxx -" 而不是其他内容

这可能是 AI 生成的脚本中的占位符写法。

`-` 在很多命令中表示"从 stdin 读取"，所以 `pigz -` 的意思本来应该是"从标准输入读取数据并压缩"。

但当这行文本被 shell 解释执行时，它会通过 PATH 再次查找 `pigz` 命令，如果找到的还是同一个损坏的文件，就形成了递归。

我们可以手动验证这个机制：

```bash
# 创建一个测试目录
$ mkdir /tmp/test_recursion
$ cd /tmp/test_recursion

# 创建一个"损坏"的命令
$ echo "testcmd -" > testcmd
$ chmod +x testcmd

# 把当前目录加到 PATH 最前面
$ export PATH="/tmp/test_recursion:$PATH"

# 执行这个命令（注意：这会快速消耗资源，立即 Ctrl+C）
$ timeout 2 ./testcmd 2>&1 | head -20
bash: warning: shell level (1000) too high, resetting to 1
bash: warning: shell level (1000) too high, resetting to 1
...
```

可以看到和我们服务器上一样的递归警告。

清理测试：

```bash
$ cd ~
$ rm -rf /tmp/test_recursion
$ export PATH=$(echo $PATH | sed 's|/tmp/test_recursion:||')
```

### 10.2 SHLVL 的含义

`SHLVL` 是 shell 的嵌套层级。可以这样观察：

```bash
$ echo $SHLVL
1

$ bash -c 'echo $SHLVL'
2

$ bash -c 'bash -c "echo $SHLVL"'
3

$ bash -c 'bash -c "bash -c \"echo \$SHLVL\""'
4
```

正常情况下：
- 登录 shell：SHLVL=1
- 在 shell 中启动子 shell：SHLVL=2

递归调用会导致 SHLVL 不断增加：

```bash
# 模拟递归（小心！会快速增长）
$ (bash -c 'for i in {1..10}; do bash -c "echo SHLVL=\$SHLVL"; done')
SHLVL=2
SHLVL=2
SHLVL=2
...
```

bash 在达到 1000 时会重置并输出警告：

```
bash: warning: shell level (1000) too high, resetting to 1
```

这是 bash 的自我保护机制，但重置后递归还会继续。

### 10.3 为什么 SSH 登录不了

用 `ss` 命令看 TCP 连接状态：

```bash
$ ss -tn | grep :22
ESTAB  0  0  server_ip:22  client_ip:54321
```

连接是 `ESTAB`（已建立）状态，但卡在那里了。

当系统内存和进程数耗尽时：

```bash
# 当时的资源状态（从 sar 重建）
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           754G        752G        788M         12G        1.2G         200M
Swap:          4.0G        4.0G          0B
```

此时：
- kernel 仍能处理网络包（所以 ping 通，TCP 能建立）
- 但 sshd 无法 fork 出新进程处理登录

```bash
# sshd 的日志（事故时）
$ journalctl -u sshd --boot=-1 --since "00:15" --until "00:20"
Sep 30 00:17:23 sshd[12345]: Accepted connection from client_ip port 54321
Sep 30 00:17:23 sshd[12345]: error: fork: Cannot allocate memory
Sep 30 00:17:45 sshd[12346]: Accepted connection from client_ip port 54322
Sep 30 00:17:45 sshd[12346]: error: fork: Cannot allocate memory
```

即使 fork 成功，也可能因为内存不足无法分配 PTY：

```bash
Sep 30 00:18:12 sshd[12389]: error: pty_allocate: Cannot allocate memory
```

最终表现就是：
- 客户端：`Connection established` 后卡住
- 服务端：sshd 无法创建会话
- 结果：永远等不到登录提示

验证当前系统可用资源（恢复后）：

```bash
$ cat /proc/sys/kernel/pid_max
4194304

$ ps -e --no-headers | wc -l
1145

$ echo "当前进程数占 PID 空间的比例: $(echo "scale=2; 1145/4194304*100" | bc)%"
当前进程数占 PID 空间的比例: 0.02%
```

正常情况下进程数占用不到 0.1%，事故时达到了 0.6%（25,462 / 4,194,304）。

### 10.4 内存是怎么被吃光的

每个 bash 进程大约占用：

```bash
$ ps aux | grep bash | head -1 | awk '{print $6}'
3456

# 单位是 KB，转换成 MB
$ echo "scale=2; 3456/1024" | bc
3.38
```

单个 bash 进程约 3.38 MB。

如果有 25,462 个 bash 进程：

```bash
$ echo "scale=2; 25462 * 3.38 / 1024" | bc
84.03
```

bash 本身占用约 84 GB。

但还有进程栈、文件描述符、内核数据结构等开销：

```bash
# 查看进程限制
$ ulimit -a | grep -E "open files|max user processes|stack size"
open files                      (-n) 1048576
max user processes              (-u) 772700
stack size              (kbytes, -s) 8192
```

每个进程：
- 栈：8 MB
- 文件描述符表：若干 KB
- task_struct 等内核结构：~1-2 KB

粗略计算（25,462 个进程）：

```bash
$ echo "scale=2; 25462 * (3.38 + 8 + 0.1) / 1024" | bc
285.73
```

约 285 GB，这还没算上其他正常进程和系统开销。

加上正常的生信任务（一些任务本身就占几十 GB 内存），754 GB 被吃光就不奇怪了。

## 11. 总结

这次事故的完整链条：

```
9月18日 AI 帮忙安装工具
    ↓
通过 SSH 管道执行批量脚本
    ↓
脚本先写 "xxx -" 占位符，再写完整内容
    ↓
执行到一半被 Ctrl+C 中断
    ↓
多个系统命令只剩下 "xxx -"
    ↓
修复了部分文件，但漏掉了 pigz/unpigz
    ↓
9月30日 某任务调用 unpigz
    ↓
触发 pigz 无限递归
    ↓
bash 进程暴增，内存耗尽
    ↓
SSH 无法登录，只能重启
```

核心问题不是某个程序的 bug，而是：
1. 脚本设计不当（先覆盖文件，再写内容）
2. 操作被中断（没有原子性保证）
3. 检查不彻底（漏掉了部分损坏文件）

最终的解决办法也很直接：
- 恢复所有损坏的文件
- 全面检查确保没有遗漏
- 以后避免用管道执行危险操作

754 GiB 内存能被吃光，不是因为某个程序占用太多，而是因为几万个 bash 进程同时存在。

这次事故提醒我：系统维护不能只看"当前有问题的地方"，而要全面检查"可能被影响的所有地方"。
